================================================================================
PROJECT CONTEXT & ARCHITECTURAL DIRECTIVES
Woodsmen: Co-Op Multiplayer (Lumberjack & Warrior)
================================================================================

1. PROJECT OVERVIEW & GAME VISION
--------------------------------------------------------------------------------
- Genre: Co-Op Multiplayer Action & Survival / Resource Gathering.
- Core Fantasy: 
  * Lumberjack: Focuses on environmental interaction, cutting trees, gathering wood, clearing paths, building/crafting, and harvesting raw materials.
  * Warrior: Focuses on protecting the team, fighting AI monster hordes, melee combat, crowd control, and defending the gatherer.
  * Shared Loop: Players collect materials (wood, monster drops, minerals) to craft and upgrade weapons, tools, and defenses in a shared synchronized world.

2. CORE ARCHITECTURAL PILLARS & TECH STACK
--------------------------------------------------------------------------------
- Networking: Mirror Networking
  * Server-authoritative logic with responsive client-side interpolation/prediction.
  * Efficient NetworkTransform / NetworkAnimator or custom synced state to minimize bandwidth.
- Locomotion System: Pure Script / Code-Driven (NO Root Motion)
  * Script/physics-based movement (CharacterController or Rigidbody with deterministic math).
  * Eliminates Root Motion bandwidth synchronization bloat and ensures tight, responsive controls.
  * Maximizes crowd scalability for dozens of AI enemies chasing players simultaneously.
- AI & Pathfinding: Pre-Baked NavMesh + Dynamic NavMeshObstacle Carving
  * NavMesh baked once on a flat ground plane.
  * Destructible objects (e.g. trees, rocks, barricades) use NavMeshObstacle with 'Carve = true'.
  * Zero runtime NavMesh rebaking: cutting a tree opens holes in the NavMesh dynamically and cheaply.
- Interaction Feedback & Procedural Animation: PrimeTween
  * Physical impacts and hit reactions use procedural squash-and-stretch and scaling via PrimeTween.
  * Eliminates bloated, sluggish Animator state machines for simple hit/impact/harvest reactions.
- Visual Effects & Object Pooling: Zero-GC Ring Buffer VFXManager
  * Pre-warmed circular pools for impact VFX (wood splinters, dust puffs, combat hits).
  * Hierarchical playback (`Play(withChildren: true)`) ensuring composite parent/child particle systems fire synchronously.
  * Fully decoupled from world props (zero manual scene references required on environment prefabs).
- Combat & Harvesting Hitbox System: Universal WeaponHitbox
  * Dedicated modular hitbox component (`WeaponHitbox.cs`) and integrated fallback options on characters.
  * Supports Sphere and Box geometries, local center offsets, Euler rotation alignment, and bone socket anchoring.
  * Real-time Scene view gizmo visualizations (active/inactive states) and non-allocating physics overlap queries.
- Camera & Screen Shake: Cinemachine + Cinemachine Impulse
  * Cinemachine Virtual Cameras for dynamic framing.
  * Cinemachine Impulse for camera shakes triggered via 6DOF Perlin noise.
  * Overlapping shakes resolve natively without manual coroutine overhead.

3. STRICT OPTIMIZATION DIRECTIVES
--------------------------------------------------------------------------------
- [Rule 1] NO standard Coroutines (IEnumerator) for mathematical updates, timers, or camera shakes. Use PrimeTween or tick updates.
- [Rule 2] NO runtime NavMesh rebaking. Always use pre-baked meshes with dynamic NavMeshObstacle carving.
- [Rule 3] NO Root Motion for standard movement. Keep locomotion purely script/math-driven for network determinism and low overhead.
- [Rule 4] Procedural animations (PrimeTween) over Animator states for hit reactions, object scaling, squash & stretch, and color flashes.
- [Rule 5] Zero/minimal Garbage Collection (GC) in hot loops (Update/FixedUpdate/Network updates). Cache non-allocating queries (e.g., Physics.OverlapSphereNonAlloc).
- [Rule 6] Input System Architecture: Exclusively use Unity's New Input System Action Maps. NEVER use legacy `Input.GetKeyDown`, `Input.GetAxis`, or polling.
- [Rule 7] Defensive Component Retrieval: Avoid direct unchecked `GetComponent` / `GetComponentInParent`. Always use `TryGetComponent` or null-safe retrieval patterns to gracefully handle missing references.
- [Rule 8] Memory & Allocation Discipline: Cache references in `Awake`/`Start`, unsubscribe from events and disable/dispose Input Actions in `OnDisable`/`OnDestroy` to prevent memory leaks, and free/pool allocations wherever possible.
- [Rule 9] Universal Action Input Mapping: Characters share standard top-down inputs (`Move`, `Look`, `PrimaryAction`, `SecondaryAction`). Specific role logic (e.g. Lumberjack chopping vs Warrior attacking) hooks into these shared actions rather than creating fragmented action maps.
- [Rule 10] Preserve Manual Developer Control: NEVER use `[InitializeOnLoadMethod]` or automatic domain reload hooks that overwrite Animator Controllers, Avatar Masks, Prefabs, or Scene Assets. Setup utilities must be strictly explicit via `[MenuItem]` so the developer retains 100% control over fine-tuned adjustments.
- [Rule 11] Mandatory Object Pooling for Transient Assets: NEVER use runtime Instantiate() / Destroy() for frequently spawned or transient objects (visual effects, particle systems, audio one-shots, projectiles, damage numbers, dropped resource pickups). Always pre-warm and reuse instances using dedicated, zero-GC object pools (e.g. VFXManager, circular ring buffers, or UnityEngine.Pool) to eliminate Garbage Collection spikes, prevent frame-rate hitching, and decouple scene dependencies.
- [Rule 12] Server-Authoritative Health & Combat Architecture: Character health, damage calculation, and death states must be server-authoritative (`isServer`) with client synchronization via Mirror `[SyncVar]` hooks and `[ClientRpc]` event dispatches. Always provide defensive offline/single-player fallbacks (`!NetworkClient.active && !NetworkServer.active`) so characters and combat actions are 100% testable in any scene without network hosting (Rule 3). All damageable entities (players, trees, monsters, destructibles) must implement `IDamageable` for unified combat routing. Screen shakes and camera feedback must be strictly isolated to the damaged player (`isLocalPlayer`).

4. CLI & TOOLING ENVIRONMENT SETUP
--------------------------------------------------------------------------------
- Machine & Project CLI Enabled:

  * Direct CLI accessibility accelerates development speed and keeps iteration feedback loops short.
